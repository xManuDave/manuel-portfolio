Kurzfassung

Von der Team-Vorlage zum bewerteten Endprodukt

Ausgangslage

Kursvorgabe war ein leeres Setup-Repository mit Issue-Templates für Business Requirements und User Stories. Nach Release 1 stand ein funktionaler CRUD-Prototyp mit DBLP-Live-Import — aber auf einem nicht gemergten Branch, mit einem 328-Zeilen-„God Controller" und ohne Architekturdokument. Das war der Ausgangspunkt für Release 2.

Ergebnis

Eine schichtenweise MVC-Anwendung mit fünf domänenspezifischen Controllern, einer Service-Schicht, SQLite-Persistenz und 302 JUnit-Tests bei 87 % Branch Coverage. 15 Business Requirements sind über Software Requirements bis zu einzelnen User-Story-Issues zurückverfolgbar, jede Änderung lief über Feature-Branch und Pull Request.

GitHub-Workflow

Ein Ablauf für jede Änderung, kein Ausnahmefall

Nach dem kritischen R2-Zwischenfeedback („nur 1 PR im ganzen Repo") galt für den Rest des Projekts eine feste Regel: keine Commits direkt auf main, jede Änderung als Feature-Branch mit Pull Request und Teammate-Review.

Vereinfachte Darstellung des tatsächlichen Ablaufs — jede der 38 gemergten PRs folgte diesem Muster: Branch je Issue, Commits mit Issue-Referenz, Review, Merge, Tag am Release-Ende.
Eigenes Werkzeug — Git Wizard (PowerShell + GitHub CLI)
1. Start a new feature → Branch aus offenem Issue erzeugen
2. Save progress → mvn clean verify + Commit mit Issue-Referenz
3. Submit for review → Push + gh pr create
4. Merge & cleanup → Merge, Branch löschen, zurück zu main
5. Create release tag → R1 / R2 / R3 / Final-Release

Um den Workflow im Team konsistent zu halten statt ihn nur zu dokumentieren, entstand ein interaktives CLI-Menü mit sechs Optionen und kontextsensitiver Hilfe — inklusive eigener Sequenzdiagramme je Schritt.

Architektur

Entscheidungen, die aus Feedback entstanden sind

Service-Schicht
Controller ohne Geschäftslogik.

Nach dem R2-Zwischenfeedback („Controller trägt Logik direkt") wurde zwischen Controllern und AppData eine eigene Service-Schicht eingezogen — CommunityService, ConferenceService, JournalService und weitere — wodurch Geschäftslogik erstmals isoliert testbar wurde.

Fünf Controller
Ein View, ein Controller.

Der ursprüngliche 328-Zeilen-MainController wurde in Community-, Conference-, Journal-, Researcher- und DblpController aufgeteilt; MainController selbst ist heute nur noch Navigation.

SQLite-Persistenz
Ein DatabaseService für Schema und Zustand.

Ein eigener Service initialisiert das Schema, lädt den Zustand beim Start und speichert transaktional nach jeder erfolgreichen Service-Operation. Lokale .db-Dateien sind bewusst von Git ausgeschlossen.

Coverage-Fokus
87 % Branch Coverage, gezielt auf Fachlogik.

JavaFX-Controller und der App-Launcher sind aus der Coverage-Messung ausgenommen — gemessen wird, was sich sinnvoll ohne UI-Testframework prüfen lässt: Modell- und Service-Schicht, inklusive Rand- und Fehlerfällen.

KI-Einsatz offengelegt
Dokumentiert statt versteckt.

Ein eigenes docs/ai-note.md hält fest, wo KI-Unterstützung genutzt wurde — UI-Modernisierung, SQLite-Integration, gezielte Zusatztests für ungetestete Zweige — jeweils im Team geprüft, bevor es in main ging.
